# 9f Session 1 — Multi-turn chat persistence + plumbing (Implementation Plan)

**Spec:** `docs/design/2026-07-15-9f-multi-turn-chat-design.md`
**Date:** 2026-07-15

**Goal:** Replace one-shot `/ask` with server-owned, per-user persistent conversation
threads, and reproduce the gate-on-follow-up failure with evidence recorded in Postgres.

**Architecture:** Server owns the thread. Client sends `{conversation_id, message}`;
FastAPI loads history from Postgres, retrieves against `anchor ∪ extract(message)`, gates,
calls Claude only on pass, and persists both turns. Retrieval metadata is persisted but
never replayed into the prompt.

**Tech Stack:** Python 3.13, FastAPI, SQLAlchemy 2.0, Alembic, Postgres 16 (Docker Compose),
pytest (new), ChromaDB, Claude `claude-sonnet-4-6`.

## Global Constraints

- **Session 1 makes zero changes to the retrieval path.** `retrieve_ranked`, gate logic,
  `SCOPE_THRESHOLD`, and the embedder are out of scope.
- **Stage git by explicit filename.** Never `git add .`, never `commit -am`.
- **Held files must never be staged:** `rag/embedder.py`, `.gitignore`,
  `evals/calibrate_threshold.py`, `evals/embedding_ab.py`.
- **Push stays held.** `main` auto-deploys; the mpnet batch is undeployed.
- **`requirements.txt` is edited terminal-only** (`WriteAllLines` + `UTF8Encoding $false`).
  Never via VS Code — BOM re-stamping. Verify with `Format-Hex`.
- **Runtime verification runs on `uvicorn api:app` with no `--reload`.** One process, zero
  ambiguity about which bytes are live.
- **Full-file review before modifying any existing file.** No guessed signatures.
- `extract()` returns an empty scope in Session 1. The seam exists; Session 2 fills it.

## Deviation from the writing-plans skill (named, not silent)

The skill prescribes complete code in every step. Two reasons this plan gives **exact
interfaces** instead of full bodies for some tasks:

1. **Three of the files are unreviewed.** `main.py`, `api.py`, and `index.html` have not been
   read this session. Writing code against them would be guessing signatures — the exact
   thing this project's process rules forbid. Each task that touches them opens with a review
   step.
2. **Execution is interactive, not agentic.** The skill's handoff assumes a subagent
   executing autonomously. Naga types every line manually, one step at a time, with code
   delivered just-in-time per step. The plan's job here is task order, exact interfaces,
   verification, and commit points — enough that no task is ambiguous.

The `Interfaces` blocks are therefore load-bearing: they are the contract each task must hit.

## Spec correction found during planning

**The spec says `title` is "first ~60 chars of first user message" and also returns `title`
from `POST /conversations`. Those contradict — at creation there is no first message yet.**

Resolution: `title` is **nullable**, set on the first successful `/ask` in that thread. The
sidebar renders "New thread" for a null title (frontend concern, not a DB default). Applied
below; update the spec to match when convenient.

```python
from sqlalchemy.orm import Session   # plain, NOT aliased — see the trap below

```

**Naming trap — read this before writing the imports.** In `session_service.py`, `DbSession`
is an alias for the auth **`Session` model** (`import Session as DbSession`), adopted to dodge
the collision with SQLAlchemy's `Session`. `chat_service.py` imports no `Session` model, so
there is no collision here and `Session` means SQLAlchemy's session, unaliased. **Do not
carry `DbSession` over from `session_service.py` — it would mean the opposite thing in the
two files, which is worse than either convention alone.** The injected param is still named
`db`, never `session`.

`get_history` returns Anthropic messages format — `[{"role": ..., "content": ...}]` — and
**excludes gate-rejected pairs**: a user row whose `retrieval[-1]["gate"] != "pass"` is
dropped along with its assistant row. This is decision 2.6; it is the single most
test-worthy behaviour in the file.

`get_conversation` returns `None` for both "doesn't exist" and "not this user's" — the route
layer turns both into 404. Ownership is enforced **here**, in the query's `WHERE user_id`,
not in the route. That is what makes the IDOR test meaningful.

The injected param is named `db`, never `session` — the established house rule.

### Task 4: `/ask` contract change

**Files:**
- Modify: `main.py` (`ask_igla` signature)
- Modify: `api.py` (`/ask` route)

**Interfaces — Consumes:** `chat_service.get_history`, `chat_service.add_message`,
`chat_service.get_conversation`, `chat_service.set_title_if_absent`.

**Interfaces — Produces:**
```python
class AskRequest(BaseModel):
    conversation_id: UUID
    message: str          # .strip(); reject empty at the boundary
```
`POST /ask` → `{answer, conversation_id, message_id}`.
`team_id` is **removed** from `/ask`. It lives on the conversation row now.

Route body order — this is the contract, and it is the whole task:
```
require_user
get_conversation(...) or 404
entity_scope = {"team_ids": [conv.team_id]}     # extract() is a no-op in Session 1
retrieve_ranked(message, entity_scope)
add_message(role="user", entity_scope=..., retrieval=[{...}])   # ONE write, before Claude
if gate rejects:
    add_message(role="assistant", content=<rejection text>)
    return                                       # no Claude call, zero tokens
history = get_history(conversation_id)           # gate=="pass" pairs only
answer = ask_igla(message, retrieved_context, history)
add_message(role="assistant", content=answer)
set_title_if_absent(conversation_id, message)
touch conversations.updated_at
```
